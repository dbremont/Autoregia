CTES

Computation Task Execution System

A system that manages the lifecycle of tasks — from submission to completion: how specified work is emitted, stored, scheduled, dispatched, executed, and has its results returned reliably. Where CES provisions the environments work runs in, CTES is the discipline of the work itself: queues, schedulers, dispatchers, workers, and result channels.

designed — not yet implemented The full design is written — task formulation, the execution workflow, taxonomy, lifecycle state machine, coordination, failure handling, trade-offs, and verification. This plate reserves CTES's place in the toolbox; the spec lives at spec/ctes/.
The Model
OBJECTIVE
What is to be accomplished — the task's stated purpose. The unit of intent.
INPUT · OPERATION
Information execution operates on, and what is to be done to it. The unit of specification.
OUTPUT · CONSTRAINTS
The expected result and the conditions governing execution — deadlines, resources, policy. The unit of contract.
DEPENDENCIES · MODE
Other tasks or resources required, and when the result is expected — synchronous or asynchronous. The unit of ordering.
The Execution Workflow
Task Emitter ──► Task Submission ──► Task Storage / Queue
                                        │ stores pending work
                                        ▼
               Scheduling / Dispatch ──► Task Executor
                                        │ performs work
                                        ▼
               Task Result ──► Result / Feedback Channel
                                        │
                                        ▼
                                  Task Emitter ──► (subsequent tasks)

Cross-cutting mechanisms operate across this structure: state management, leases, heartbeats, timeouts, retries, logging, and monitoring.

Temporal Modes
SYNC
Synchronous
The emitter waits for the execution result: emitter → execute → result → emitter.
ASYNC
Asynchronous
The emitter submits and continues; the result arrives later through the feedback channel.
The Space · Task Execution Systems
TypeExecutesInstances
Function Executiona discrete function in response to a taskAWS Lambda, OpenFaaS
Job Executionsubmitted jobs via a queue and worker poolCelery, Sidekiq
Workflow Executionmultiple tasks coordinated by dependencies and workflow logicTemporal, Apache Airflow
Build Executiontransformation of source artifacts into derived artifactsBazel, Buck, Ninja
Batch Executioncollections of tasks or computations as batchesApache Hadoop, Apache Spark
Stream Processingcontinuous computation as data arrives through a streamApache Flink, Kafka Streams
Serverless Executiontasks without user-managed execution infrastructureAWS Lambda, Google Cloud Functions
Distributed Executiontasks across machines, coordinating resources and executionRay, Dask
Cluster Executiontasks across a managed cluster under resource and scheduling constraintsKubernetes, Slurm

These are not separate categories — they are different configurations of the same underlying task-execution problem.

Task Lifecycle
Created → Submitted → Pending → Dispatched → Running
                                            ├─► Completed
                                            └─► Failed ─► Retry → Pending
                                                       └► Abandoned
Cancellation may transition a task from several intermediate states to Cancelled.
